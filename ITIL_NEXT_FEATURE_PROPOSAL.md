# ITIL 4 Helpdesk – Next Feature Proposal

## 1. Context and current ITIL coverage

This repository already delivers a strong ITIL 4 aligned helpdesk on Odoo 18 CE:

- SLA & priority matrix via [`HelpdeskSLAPolicy(models.Model)`](helpdesk_mgmt_sla/models/helpdesk_sla_policy.py:6) and [`HelpdeskTicketPriority(models.Model)`](helpdesk_mgmt_sla/models/helpdesk_sla_policy.py:169)
- Problem Management and Known Error Database via [`HelpdeskProblem(models.Model)`](helpdesk_mgmt_problem/models/helpdesk_problem.py:6) and [`HelpdeskKnownError(models.Model)`](helpdesk_mgmt_problem/models/helpdesk_known_error.py:6)
- Knowledge Management via [`HelpdeskKnowledgeArticle(models.Model)`](helpdesk_mgmt_knowledge/models/helpdesk_knowledge_article.py:6)
- AI Agent Orchestration for incident automation via [`HelpdeskAIAgent(models.Model)`](helpdesk_mgmt_ai_agent/models/helpdesk_ai_agent.py:10)
- Overall ITIL + AI positioning documented in [`README_AI_ITIL.md`](README_AI_ITIL.md:1) and Odoo 18 migration notes in [`MIGRATION_ODOO18.md`](MIGRATION_ODOO18.md:1)

From an ITIL 4 practice perspective, the current scope covers primarily:

- Incident Management (enhanced helpdesk tickets + AI classification/routing)
- Service Level Management (SLAs, monitoring, escalation)
- Problem Management (problems, known errors, KEDB)
- Knowledge Management (KB, portal exposure, usage metrics)

## 2. Gap analysis – what is missing for the “next” ITIL feature?

Key ITIL 4 practices that are not yet explicitly modelled in the codebase, but are natural next steps on top of the existing modules:

1. **Major Incident Management**
   - Fast‑track handling for high‑impact incidents
   - Dedicated war‑room style coordination and communication
   - Post‑Incident Review (PIR) records strictly linked to Problems and Known Errors

2. **Change Enablement** (Change Management)
   - Formal Requests for Change (RFC) raised from Problems / Known Errors / Tickets
   - Risk and impact assessment, CAB approval workflow
   - Change calendar and implementation window tracking
   - Integration with project tasks for implementation work

3. **Continual Improvement & Metrics** (lightweight)
   - KPIs around incident, problem, and change practices
   - Simple improvement register linked back to tickets/problems/changes

For this iteration, we propose to focus on a **combined “Major Incident & Change Enablement” feature**, leveraging the existing SLAs, Problems, Known Errors, Knowledge Base and AI Agents.

## 3. Proposed feature scope

### 3.1. Major Incident Management

Introduce a Major Incident layer on top of standard helpdesk tickets:

- Ability to **flag a ticket as a Major Incident**
- Ability to **group multiple related incidents** under a single Major Incident record
- Dedicated workflow and timeline for major incidents:
  - Identified → In Progress → Stabilized → Resolved → Closed
- Automatic relationships with:
  - Existing Problems (`helpdesk.problem`)
  - Known Errors (`helpdesk.known.error`)
  - Post‑Incident Review (PIR) document
- Tight integration with SLA policies so that breach risk and business impact are clearly visible

### 3.2. Change Enablement

Provide a structured way to implement permanent fixes emerging from Problems / Known Errors / Major Incidents:

- **Request for Change (RFC)** record type, linked to:
  - One or more Problems (`helpdesk.problem`)
  - One or more Known Errors (`helpdesk.known.error`)
  - Optional Major Incident
- Core lifecycle: Draft → Assessment → CAB Approval → Scheduled → Implementing → Completed / Failed / Rolled Back
- Risk and impact fields (business, technical, security, compliance)
- Ability to schedule changes in a **Change Calendar** view
- Optional **link to implementation tasks** using existing project / task integration

### 3.3. Reporting and metrics (minimal first version)

- Major incident dashboard widgets (count, MTTR, open by priority)
- Basic change metrics (changes per period, success vs failure, changes per service/team)

## 4. High‑level technical design

### 4.1. New Odoo module: `helpdesk_mgmt_change`

Add a new addon to keep responsibilities separated and optional:

- Manifest: `helpdesk_mgmt_change/__manifest__.py` with dependencies on `helpdesk_mgmt`, `helpdesk_mgmt_problem`, and `helpdesk_mgmt_project` (for implementation tasks)

#### 4.1.1. Data model – new models

1. **Major Incident**

   - Model name: `helpdesk.major.incident`
   - Key fields (non‑exhaustive):
     - `name` (Char) – Major incident title
     - `number` (Char) – Autogenerated sequence (e.g. MI0001)
     - `state` (Selection) – identified / in_progress / stabilized / resolved / closed / cancelled
     - `priority` (Selection) – aligned with `helpdesk.ticket.priority.value`
     - `description` (Html)
     - `impact_summary` (Html) – business impact description
     - `affected_users_estimate` (Integer)
     - `ticket_ids` (Many2many to `helpdesk.ticket`)
     - `problem_id` (Many2one to `helpdesk.problem`)
     - `known_error_id` (Many2one to `helpdesk.known.error`)
     - `sla_policy_id` (Many2one to `helpdesk.sla.policy`, optional)
     - `pir_document` (Html) – Post‑Incident Review
     - `start_date`, `stabilized_date`, `resolution_date`, `closed_date` (Datetime)
     - `manager_id` (Many2one to `res.users`)
     - `color` (Integer) – for kanban

2. **Request for Change (RFC)**

   - Model name: `helpdesk.change.request`
   - Key fields:
     - `name` (Char) – RFC short title
     - `number` (Char) – Sequence code `helpdesk.change.request`
     - `state` (Selection): draft / assessment / pending_cab / approved / scheduled / implementing / completed / failed / rolled_back / cancelled
     - `type` (Selection): standard / normal / emergency
     - `risk_level` (Selection): low / medium / high / critical
     - `impact` (Selection): low / medium / high / critical
     - `backout_plan` (Html)
     - `test_plan` (Html)
     - `implementation_plan` (Html)
     - `scheduled_start`, `scheduled_end` (Datetime)
     - `actual_start`, `actual_end` (Datetime)
     - `problem_ids` (Many2many to `helpdesk.problem`)
     - `known_error_ids` (Many2many to `helpdesk.known.error`)
     - `major_incident_id` (Many2one to `helpdesk.major.incident`)
     - `ticket_ids` (Many2many to `helpdesk.ticket`)
     - `project_id` / `task_ids` (links to implementation work, via `project.task` or `helpdesk.task`)
     - `requested_by_id`, `change_manager_id`, `cab_approver_ids` (Many2one/Many2many to `res.users`)
     - `approval_notes` (Html)

### 4.2. Extensions to existing models

1. **helpdesk.ticket**

- New fields (in a lightweight `helpdesk_mgmt_change/models/helpdesk_ticket.py` extension):
  - `is_major_incident` (Boolean)
  - `major_incident_id` (Many2one to `helpdesk.major.incident`)
  - `change_request_ids` (Many2many to `helpdesk.change.request`)

2. **helpdesk.problem**

- Small extension via a new file `helpdesk_mgmt_change/models/helpdesk_problem.py`:
  - `major_incident_ids` (Many2many to `helpdesk.major.incident`)
  - `change_request_ids` (Many2many to `helpdesk.change.request`)

3. **helpdesk.known.error**

- Similar extension in `helpdesk_mgmt_change/models/helpdesk_known_error.py`:
  - `major_incident_ids` (Many2many to `helpdesk.major.incident`)
  - `change_request_ids` (Many2many to `helpdesk.change.request`)

### 4.3. Views and user experience

Key views to add under `helpdesk_mgmt_change/views/`:

1. **Major Incident**

- Menu: Helpdesk → Configuration → Major Incidents (for admins)
- Menu: Helpdesk → Major Incidents (for operational view)
- Views:
  - Kanban (status + priority colored, main KPIs on cards)
  - Tree (list of open MIs with SLA, impact, problem link)
  - Form (all details, related tickets, problem, known error, PIR)

2. **Change Requests**

- Menu: Helpdesk → Change Requests
- Views:
  - Kanban by state and type (standard/normal/emergency)
  - Calendar (change calendar by `scheduled_start` / `scheduled_end`)
  - Tree (compact list view)
  - Form (full RFC information, related tickets/problems/known errors/tasks)

3. **Ticket form integration**

- Smart buttons on ticket form to:
  - View linked Major Incident
  - View/create Change Requests
- Decoration and badges when a ticket is part of a Major Incident or RFC

### 4.4. AI & automation hooks

Use the existing AI framework in [`helpdesk_mgmt_ai_agent`](helpdesk_mgmt_ai_agent/models/helpdesk_ai_agent.py:10) to enhance the new workflows without hard‑coding any external AI provider:

- Extend `helpdesk.ai.classification` to suggest **Major Incident flag** and **risk level** based on:
  - Urgency and impact keywords
  - Affected users estimates
  - Priority (`helpdesk.ticket.priority`)
- Extend `helpdesk.ai.resolver` to suggest **candidate RFCs** when recurring incidents and a Known Error point to a structural fix.
- Extend `helpdesk.ai.knowledge.matcher` to surface **PIR documents** and **change records** as knowledge artefacts when an incident matches a previous major incident.

All of these can be implemented as incremental changes in the existing AI service models (`helpdesk_ai_classification.py`, `helpdesk_ai_resolver.py`, etc.).

## 5. Implementation plan

### Phase 1 – Core data model and basic UI

1. Create new addon `helpdesk_mgmt_change` with manifest and security (`ir.model.access.csv`).
2. Implement core models:
   - `helpdesk.major.incident`
   - `helpdesk.change.request`
3. Add tree/form/kanban/calendar views for both models.
4. Extend `helpdesk.ticket`, `helpdesk.problem`, and `helpdesk.known.error` with relational links.
5. Add smart buttons and basic decorations on ticket and problem forms.

### Phase 2 – Workflow refinement and integration

1. Implement full state machines with button actions for Major Incidents and RFCs.
2. Add onchange/constraints for scheduling (start < end, overlapping checks optional).
3. Integrate with `helpdesk_mgmt_project` to create/link implementation tasks.
4. Add basic reporting views (pivot/graph) for major incidents and changes.

### Phase 3 – AI and automation

1. Add AI suggestions for Major Incident flagging and RFC creation in the AI service models.
2. Extend resolver and pattern detector agents to:
   - Propose creation of Problems / Major Incidents / Change Requests based on thresholds.
3. Optionally add cron jobs that:
   - Scan for long‑open critical tickets and suggest converting to Major Incident.
   - Scan for recurring incidents and propose RFCs on top of existing Problems and Known Errors.

## 6. Risks, assumptions, and non‑goals

- **Risks**
  - Over‑complex workflows for small teams; we should keep all features optional and permission‑controlled.
  - Calendar performance and usability when there are many concurrent RFCs.

- **Assumptions**
  - Odoo 18 CE environment is already set up as described in [`MIGRATION_ODOO18.md`](MIGRATION_ODOO18.md:68).
  - Existing modules (`helpdesk_mgmt_sla`, `helpdesk_mgmt_problem`, `helpdesk_mgmt_knowledge`, `helpdesk_mgmt_ai_agent`, `helpdesk_mgmt_project`) are installed.

- **Non‑goals for this phase**
  - Full CMDB / configuration item modelling (future `helpdesk_mgmt_cmdb`‑style module).
  - Release management and deployment automation.
  - Deep integration with external change tools (ServiceNow, Jira, etc.).

## 7. Summary

This proposal recommends adding a dedicated `helpdesk_mgmt_change` module that introduces **Major Incident Management** and **Change Enablement** on top of the existing ITIL 4 features. It keeps the design aligned with current Odoo and ITIL conventions, integrates with existing SLAs, Problems, Known Errors, Knowledge Base and AI Agents, and leaves room for future CMDB and Release Management extensions.
